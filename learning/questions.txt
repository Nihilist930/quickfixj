1. 买方发送新单后，卖方已返回 ExecutionReport(OrdStatus=NEW)，但卖方到交易所的 Session 随即断线，系统如何判断这笔订单是否已经到达交易所，重连后如何避免重复下单？
2. 买方在极短时间内连续发送新单、改单和撤单，三类请求经过不同线程处理并发生乱序时，卖方应如何通过 ClOrdID、OrigClOrdID、OrderID 和状态机恢复正确的最终状态？
3. 买方与卖方重连后发现双方 MsgSeqNum 相差几十万条，其中包含订单确认、成交回报、心跳和行情消息，系统应如何决定哪些消息重传、哪些消息 Gap Fill、哪些业务状态通过对账恢复？
4. 卖方已经向买方发送成交回报，但买方在数据库提交前宕机，重启后 Session 重传同一条回报时，买方如何利用 ExecID、事务和幂等机制避免重复增加持仓？
5. 一笔订单被交易所部分成交后，卖方先收到成交回报，随后收到撤单成功回报，但两条消息到达买方的顺序相反，买方应如何计算 CumQty、LeavesQty 和最终订单状态？
6. 一个买方机构通过多个 FIX Session 连接同一卖方，并且多个 Session 可能使用相同的 ClOrdID，卖方应如何设计订单唯一键和跨 Session 的订单关联机制？
7. 买方使用多个基金和策略账户下单，订单经过卖方路由到多个交易所后，原始 Account(1)、Parties(453)、路由订单号和交易所订单号应如何映射，才能保证成交和持仓准确归属？
8. 卖方将一笔买方订单拆分成多个交易所子订单后，交易所分别返回多个 OrderID(37) 和 ExecID(17)，卖方应如何向买方汇总成交数量、均价、剩余数量和订单状态？
9. 买方收到一条 ExecutionReport，其中 OrdStatus=FILLED、CumQty=100、LeavesQty=0，但本地订单当前只记录已成交 60 股，系统应如何判断这是迟到回报、重复回报、数据丢失还是协议异常？
10. 卖方数据库短暂不可用，但 FIX Session 仍然收到交易所成交回报，此时系统应如何保证回报不丢失、Session 序号不紊乱，并在数据库恢复后完成订单状态和成交状态的一致性恢复？
11. 主卖方 FIX Gateway 发生故障并切换到备用实例时，两个实例如何避免同时使用同一 SenderCompID、重复发送同一订单，或者使用不一致的 MessageStore 继续通信？
12. 交易所要求在每日 Session 重置时将序号归一到 1，但买方仍有未完成订单和未确认成交，系统应如何安排 ResetOnLogon、未完成订单对账和序号重置的先后顺序？
13. 卖方收到买方订单后先返回 ExecutionReport(ExecType=NEW)，但交易所随后拒绝该订单，卖方应如何向买方区分“已接收”“已路由”和“最终被拒绝”这几个不同阶段？
14. 同一笔成交同时通过主交易 Session 和 Drop Copy Session 到达买方系统时，系统应如何判断两条消息是否代表同一个执行事件，并避免重复记账？
15. 交易所发送的 ExecutionReport 缺少买方原始 ClOrdID，但包含交易所 OrderID 和卖方路由订单号，卖方应如何完成订单关联，是否应该向买方转发或拒绝这条回报？
16. 买方发送订单时网络连接正常，但 Session.send() 返回成功后进程立即宕机，重启后无法确认该消息是否已经被卖方接收，系统应如何设计发送日志、状态查询和恢复流程？
